# self-review ログの分析

[Issue #27](https://github.com/pocke/dotfiles/issues/27) の調査を、2 台のマシンで何度でも回せる形にしたもの。

スクリプトは **数えるところまで** を担当する。どのモデルを外すか、ゲートをどう変えるかの判断は、
このディレクトリを読み込んだ Claude セッションの中で、レポートの数字を材料に人と決める。

調査のたびに手で `grep` を書き直さずに済むよう、ログの書式の揺れ (旧書式、`|` のエスケープ漏れ、
区分の注記) はパーサ側で吸収してある。書式がまた変わったら `test/` にケースを足してから直す。

## 前提

- Ruby 3.0 以上と `git`。gem は要らない (テストだけ minitest を使う)
- 手順 2 の運搬に `rsync` と `ssh`
- 対象ディレクトリの既定は `~/ghq` と `~/dotfiles`。`--root` で変えられる
- 出力先はリポジトリの外。既定は `~/self-review-analysis` (`$SELF_REVIEW_ANALYSIS_HOME` で変更可)

オプション:

| | |
| --- | --- |
| `collect.rb` | `--root PATH` (繰り返し可) / `--projects PATH` / `--out DIR` / `--machine NAME` / `--skip-transcripts` / `--force` |
| `analyze.rb` | `--in DIR` / `--out DIR` / `--force` |

**集めたものはコミットしない。** self-review のログには private リポジトリのコードとレビュー本文が
そのまま入っている。pocke/dotfiles は public なので、収集物が入ると中身が公開される。

両方のスクリプトは、出力先が git 管理下だと止まる。書き込むディレクトリ (`collect.rb` は
`<out>/collected/<machine>`、`analyze.rb` は `--out` に渡したディレクトリ) を 0700 で作り、
ファイルを 0600 で書き、そのディレクトリの中に `*` だけの `.gitignore` を置く
(`*` は自分自身にも当たるので、中身はまとめて無視される)。

`--force` はこのガードを外す。**出力先を git 管理下に置かない**かぎり要らない。
収集物ごとバージョン管理する private なリポジトリに出力先を置く運用でだけ使う。

## 材料

| 欲しい数字 | どこから取るか |
| --- | --- |
| ラウンド数、指摘、重大度、区分、対応、ラウンド1の指摘を出したモデル、verdict | `.claude/artifacts/**/self-review.md` |
| スイートの実行時間 | 同上 (ラウンド見出し直下のスイート行) |
| run とラウンドの所要時間、sub agent 1 体ごとのモデルとトークン | `~/.claude/projects/<project>/<session>/subagents/agent-*.jsonl` と同名の `.meta.json` |
| セッション全体のコスト | `~/.claude/projects/<project>/<session>.jsonl` の `totalCostUSD` |

self-review.md にはトークンも所要時間も残らないので、待ち時間とコストの判断はトランスクリプト側が要る。
ログとトランスクリプトは、マシン・リポジトリ・ブランチ・時刻で突き合わせる (完全な鍵は無い。後述の限界を読むこと)。

## 手順

### 1. 各マシンで集める

2 台とも、このブランチをチェックアウトして実行する。

```
cd ~/dotfiles
git fetch origin && git switch claude/self-review-log-analysis
ruby tools/self-review-analysis/collect.rb
```

2 台のホスト名が同じだと、収集物が同じディレクトリに落ちて片方が消える。
先に両方で `hostname` を確認し、同じなら片方に `--machine box-b` のような別名を付ける。

`~/self-review-analysis/collected/<machine>/` に次が出る。

| ファイル | 中身 |
| --- | --- |
| `runs.jsonl` | run 1 本 1 行。ラウンド、レビュアー、変更規模 |
| `findings.jsonl` | 指摘 1 件 1 行。重大度・区分・対応・モデル |
| `sessions.jsonl` `agents.jsonl` `usage_events.jsonl` | トランスクリプト側の時刻とトークン |
| `bundle.md` | 全ログの原文に、どのリポジトリのどのブランチかの見出しを付けて連結したもの |
| `warnings.jsonl` | パーサが読み切れなかった行。最初に見る |
| `meta.json` | 収集日時と件数 |

`--skip-transcripts` を付けるとログだけ集める。

### 2. 1 台に集約する

2 台目の `collected/<hostname>/` を、1 台目の `collected/` の下にディレクトリごと置く。

```
# 2 台目で
rsync -a ~/self-review-analysis/collected/<2台目のhostname> <1台目>:~/self-review-analysis/collected/
```

`analyze.rb` は `collected/` の下を全部読む。同じログを 2 台で集めていると run も指摘も二重になるので、
その場合は report の 1 節が警告を出す (片方の `collected/<machine>` を消して集計し直す)。

### 3. 集計する

```
ruby tools/self-review-analysis/analyze.rb
```

`~/self-review-analysis/analysis/` に 3 つ出る。

- `report.md` — 8 節の集計 (収集の範囲 / run 一覧 / リポジトリ別 / ラウンド1のモデル / 収束性 / 待ち時間 / トークン / 棚卸しの件数)
- `summary.json` — 同じ数字の機械可読版。追加の集計をするときの入力
- `triage.md` — 「ゲートで記録のみ」「見送り」「打ち切り」「扱いが割れたもの」「分類できなかった対応」を run 横断で並べたチェックリスト

### 4. 分析セッションを立ち上げる

`~/dotfiles` でセッションを開き、次を投げる。

```
Issue #27 の調査をする。手順は tools/self-review-analysis/README.md の「5. セッションの中でやること」。
集計済みのデータは ~/self-review-analysis/analysis/ にある。
```

3 までを済ませていない場合は、セッションの中で `collect.rb` と `analyze.rb` を走らせてよい
(2 台目のぶんは手で運ぶ必要がある。1 台分だけで進めるなら、その旨をレポートに書く)。

### 5. セッションの中でやること

数字を読む順番。**先に品質を確認してから中身を読む。** 母数が偏っていると、以降の判定が全部ずれる。

1. **データの品質**
   - `warnings.jsonl` を全部読む。パーサが落とした指摘があると件数が過小になる
   - `report.md` 1 節の突合率。トランスクリプトと結び付かなかった run は、待ち時間とコストの集計から抜けている
   - 変更規模の `source` 内訳。`base..branch` 以外は代用値
   - リポジトリの偏り (3 節)。ドキュメントだけの run とコードの run が両方入っているか
2. **ラウンド1のマルチモデル化** (4 節と 7 節) — モデルごとのユニーク指摘数、重複率、ユニーク指摘1件あたりのコスト、所要時間の中央値と最大
3. **収束性** (5 節) — 区分の推移、ラウンド数の分布、ゲートで記録のみにした件数
4. **待ち時間** (6 節) — ラウンドごとの最遅レビュアー、モデルを外したときに縮む時間、スイートの閾値に当たった件数
5. **棚卸し** (`triage.md`) — 同じ根の指摘をまとめ、skill を直すもの / 個別の変更の問題 / 対応不要 に振り分ける。
   複数の run で繰り返し出ているものが、skill 側の欠陥の候補
6. **レポートを書く** — 下の「決めること」に答える形で、根拠の数字を添えて

### 6. 決めること

Issue #27 が挙げている 3 つに、待ち時間とトークンコストの観点を足したもの。

1. **ラウンド1のモデル構成** — 直積のままか、観点ごとに選ぶか、減らすか。
   材料はユニーク指摘数・重複率・ユニーク指摘1件あたりのコスト・最遅モデルの分布
2. **`fresh-surface` をゲートに含めるか** — ラウンド数の分布と `fresh-surface` の比率
3. **修正を最小スコープに縛る対策を入れるか** — `fresh-surface` が支配的な run がどれだけあるか
4. **待ち時間を縮められるか** — ラウンド1は並列なので、待ちは最遅の 1 体で決まる。
   6 節の「そのモデルを外したときに縮む待ち時間」は、そのモデルの sub agent を全部消して測り直した差
5. **ゲートの 2 規則の優先順位** (Issue のコメント) — `triage.md` の「ゲートの規則が競合した箇所」に実例が出ているか
6. **スイートの閾値の較正** (Issue のコメント) — 6 節の当たり件数と、誤検知・見逃しの中身

### 7. 成果物の置き場と後片付け

レポートも、途中で書いた中間ファイルも `~/self-review-analysis/` に置く。
分析セッションは `~/dotfiles` (public リポジトリ) で動くので、リポジトリの中には何も書かない。

Issue にコメントするときに載せてよいのは、**集計値と結論だけ**。次は載せない (pocke/dotfiles は public)。

- 指摘の本文、リポジトリ内のパス、private リポジトリのコード
- private リポジトリ名、ブランチ名、`run_id`、ホスト名 (report の 2 節と 3 節に並んでいる)

分析が終わったら `~/self-review-analysis` を消す。2 台に private リポジトリのレビュー本文が残り続ける。
次に調査するときは collect からやり直せばよい。

## スクリプトの限界

数字を読むときに効いてくるもの。

- **run とセッションの突合は時刻ベース。** self-review.md にセッション ID が残らないので、
  「同じリポジトリの、run の時間帯に動いていたセッション」を候補にしている。確度の順に
  `branch` (同一マシン・同一ブランチ) → `time-only` → `cross-machine` → `cross-machine-time-only` で採り、
  採った種別を run ごとに記録する。run の終わりは、同じログの次の run か、最後のラウンド見出し + 1 時間。
  1 体の sub agent も、依頼元セッションの推論 1 回も、1 つの run にしか入らないので、
  隣り合う run で二重に数えることはない
- **母数が節ごとに違う。** ユニーク指摘の数はログのある run 全部から、コストと所要時間は
  トランスクリプトを突き合わせられた run からしか出ない。4 節の「ユニーク指摘1件あたり$」は
  分子と分母を突合できた run に揃えてあるが、その本数は同じ節の上の表とは違う
- **観点ごとのモデルの適性はログから出せない。** 指摘テーブルに観点の列が無く、ラウンド1では
  観点をまたいで同じ指摘を 1 件にまとめる決まりなので、指摘と観点が結び付かない。
  レポートに出るのは「セキュリティとそれ以外で、どのモデルを何体起動したか」まで。
  観点ごとに選ぶ設計を検討するなら、bundle.md を読むか、次回から指摘テーブルに観点の列を足す
- **レビュー用の sub agent の判定は description の正規表現** (`review|レビュー|verif|検証|round N|ラウンドN|R1`)。
  同じセッションの実装用 sub agent を除くためだが、description の書き方によっては取りこぼす。
  run 一覧の agent 列は `レビュー用/その時間帯の全 sub agent` で出るので、差が大きい run は疑う
- **変更規模は best-effort。** 基準コミットが記録されていて、かつブランチが残っている run だけが
  `base..branch`。ブランチが消えている run は、ログに残った修正コミットの合計 (`fix-commits`) で代用する。
  代用値は run 一覧で `*` が付く。`base..branch` はループ中に積んだ修正コミットも含むので、
  レビュー対象そのものの規模より大きい
- **単価は claude-api skill の 2026-06-24 時点のキャッシュ** (`lib/model_pricing.rb`)。
  キャッシュ読みは入力の 0.1 倍、キャッシュ書きは 5 分 TTL が 1.25 倍・1 時間 TTL が 2 倍で計算している。
  7 節の末尾に、セッションが記録した実費との差を出しているので、そこが開いたら単価表を直す
- **ゲートの規則が競合した箇所は、該当箇所の文字列一致で拾っている。** 表記が揺れた同一箇所は拾えないので、
  件数は下限として読む
- **進行中の run も入る。** 集計中のセッションが self-review を回していると、その run が
  ラウンド数の分布や平均に入る。1 節の期間で見分ける

## テスト

```
ruby tools/self-review-analysis/test/all.rb
```

パーサ (書式の揺れ)、トランスクリプトの集計、run とセッションの突合、集計の母数、出力先のガードを覆っている。
ログの書式が変わって数字が合わなくなったら、まず失敗するテストを足してから直す。
