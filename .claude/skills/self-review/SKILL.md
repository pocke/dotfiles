# セルフレビュー

## 目的

人間がこのコードをレビューするとき、何も言うことがない状態を作る。

## 全体の流れ

1. レビュー対象の確定
2. プロジェクト固有のレビュー観点の収集
3. ラウンド1: レビュアーの起動
4. 指摘のトリアージと対応 (修正と検証 / 検証のやり直し / 見送り理由の言語化 / question への回答)
5. ラウンド2以降: 検証レビュー (ここの足切りを 4 より先に通す)
6. 終了判定とユーザーへの報告

**レビュアーを待つ間**

3 と 5 では、起動したレビュアーの結果を待つ時間が発生する。**待つ目的でツールを呼ばないこと。** sub agent が終わると通知が届き、その時点でこのスキルの続きから再開する。ターンを終えてもスキルは中断しないので、何を待っているかを 1 行書いてターンを終える。

待つための呼び出しかどうかは、コマンドやツールの種類ではなく、レビュアーの結果がもう手元にあったとしてもその呼び出しをするかで決まる。しないなら待つための呼び出しに当たる。`true`、`:`、`echo waiting`、意味の変わらない `git status` のような実行コストのほぼ無いコマンドも、`sleep` やバックグラウンドの `until` ループ、`Monitor` の起動、`ListAgents` の繰り返し、レビュアーに進捗を尋ねる `SendMessage` も、すべてこれに当たる。レビュアーの起動と、結果が返らなかったときの起動し直しは、待つための呼び出しに数えない。

レビュアーが終わる時刻は、こちらがツールを呼んだかどうかで変わらない。呼んでも早まらないので、待ち時間は縮まらない。`sleep` はさらに悪い。レビュアーが終わってもツールが返るまでは再開できないので、ツールが返るのがレビュアーの完了より後になれば、そのぶん結果を受け取るのが遅れる。

待っている間に進められる作業 (スイートの測定、linter の実行、記録ファイルの下書き) があるなら、それを先に済ませてよい。レビュアーの結果が手元にあってもいま着手する作業に限る。尽きたらターンを終える。同じ作業を繰り返すのは待つための呼び出しに当たる。

### 1. レビュー対象の確定

- スキル起動時に基準コミットを 1 つ確定する。基準は今回の作業を始める前の HEAD。セッションの記録から特定できない場合は upstream (なければデフォルトブランチ) との merge-base を使う
- 基準の確定時と各ラウンドの開始時に `git merge-base --is-ancestor <基準> HEAD` で基準が HEAD の祖先であることを検証する。rebase などで履歴が書き換わり祖先でなくなっていたら、upstream (なければデフォルトブランチ) との merge-base に基準を付け替える
- 以降すべてのラウンドで `git diff <基準>..HEAD` をレビュー対象とする。範囲を固定することで、ループ中に作った修正コミットも自動的に対象へ含まれる
- コミットメッセージはラウンド1だけレビューする。ラウンド2以降は対象外

### 2. プロジェクト固有のレビュー観点の収集

レビュアーを起動する前に、プロジェクト内のレビュー指針を探す。見つかったものはレビュアーのプロンプトに含める:

- プロジェクトの CLAUDE.md、`.claude/` 配下のドキュメント
- CONTRIBUTING.md、PULL_REQUEST_TEMPLATE、`docs/` 配下のコーディング・レビューガイド
- linter / formatter の設定 (.rubocop.yml など) から読み取れる規約

### 3. ラウンド1: レビュアーの起動

後述の「レビュー観点」を「セキュリティ」「それ以外」の 2 グループに固定する。「セキュリティ」に何を含めるかは「レビュー観点」冒頭で定義する。「それ以外」にはそれ以外の全項目を含める。セキュリティの指摘は他の観点のレビュアーとほとんど重ならない (実測で 8 割超が単独) ので、2 体に割ける run では独立させる。

レビュアーの起動数は、diffが20行未満なら1体、それ以上なら2体を起動する。

**上で決めた体数ぶん、`model: "opus"` を明示してレビュアー sub agent を起動する (2 体のときは並行起動する)。**

- `subagent_type` に `fork` を使ってはいけない。fork は `model` の指定を無視し、依頼元のコンテキストを引き継ぐので「作者の説明を鵜呑みにしない」独立性も失う
- レビュアーには他のレビュアーの存在を知らせない。同じ箇所を独立に見せるのが目的なので、分担していると伝えると和集合にならない
- レビュアー自身に sub agent を起こさせない。同時起動の上限は 20 で、超過分はキューに入らずエラーになる。子が上限に当たって落ちてもレビュアー自身は報告を返すので、調査の浅い報告が失敗と気づかれずに通る

指定したモデルで動くとは限らない。organization の allowlist でブロックされたモデルは、エラーではなく許可されたモデルに差し替わる。起動時の警告に気づいたら、記録には実際に動いたモデルを書く。

**結果の受け取りと重複排除**

- ラウンド1の全レビュアーの結果が揃うまで 4 に進まない。先に返った指摘から処理を始めると、後から来た同じ指摘をまとめられない。揃うのを待つ間は「レビュアーを待つ間」のとおりにする
- 「レビュアーへの指示」の出力形式を満たす報告だけを結果と数える。refusal やエラーの返答、途中で打ち切られた報告は、結果が返らなかったものとして扱う
- あるグループのレビュアーが結果を返さなかったときは、`model: "opus"` のまま 1 度だけ起動し直す。打ち切りの原因はレート制限や一時的な障害のことが多い。それでも結果が得られなければ、そのグループの観点はレビューを一度も通っていないことになる。その観点への指摘は、最初の検証レビュー (ラウンド2) までは区分・重大度を問わず 4 で扱う (5 の規則0)。ラウンド3以降は他の規則に従う。1 体構成でその唯一の体が結果を返さなかった場合も同じ扱いにする (両方の観点が未レビューになる)。
- 2 体で起動した run では、ラウンド1の全指摘を対象に、グループをまたいで該当箇所と指摘内容が実質同じものを 1 件にまとめる。2 グループの観点は重なることがあるので、別グループから同じ指摘が出ることがある
- 重大度が割れたら高い方を採る。question と通常の重大度が割れたら通常の重大度を採り、question の内容は根拠に畳み込む
- 同じ箇所で結論が割れたもの (一方が「バグ」、他方が「仕様どおり」) は 1 件にまとめ、対立を残したまま 4 に渡す。4 は 1 件ずつ扱いを決める場所なので、対立が見えないと判断できない

### 4. 指摘のトリアージと対応

レビュアーから受け取った各指摘について、必ずいずれかを行う。ラウンド2以降は 5 の足切りを通して 4 に戻された指摘だけがここに来る。

- **修正する**: コードを直して新しいコミットを積む。修正の範囲は指摘された箇所に限り、ついでの整形やリファクタリングを混ぜない。混ぜた分だけ次ラウンドの `fresh-surface` (5) が増え、そこに潜む must-fix と question の発見が後のラウンドに持ち越されるうえ、記録のみで閉じる should-fix・nit も無駄に積み上がる。**ループ中は amend も rebase もしない**。5 の `fresh-surface` は「直前のラウンドの修正コミット」というコミットの同一性で判定するので、履歴を書き換えるとその判定対象が消える。ログに残した「修正 (コミットハッシュ)」も無効になる。未 push のコミットの整理は 6 でループを終えてから行う
- **修正しない**: 見送る理由を明文化する。「軽微だから」「時間がないから」は理由にならない。指摘自体が誤りである根拠、または修正がかえって悪化を招く根拠を書く
- **question に回答する**: 指摘が質問なら、調査した根拠を添えて回答する。回答の結果修正が必要と分かったら「修正する」に切り替える
- **検証をやり直す**: 検証が足りないと指摘されたら、下の検証手順を踏み直して記録する。コードを直したなら対応は「修正」、記録を足しただけなら「検証のみ」

#### 修正の検証

**修正は検証してから次のラウンドへ出す。** 修正が効いているかの確認は、レビュアーではなく修正した側がやる。

**既存のテストスイートが green になったことは検証に数えない。** 指摘された不具合が未カバーなら修正前も green なので、緑でも修正の前後を区別できない。

挙動の誤りを指摘され、テストで表現できるなら、次の順で踏む (ユーザーの CLAUDE.md にあるバグ修正の手順に、前後のステップ 1 とステップ 4 を足したもの)。

1. 報告された失敗そのものを再現する。直す対象が実際にどう振る舞っているかを見てから書く。再現を飛ばして書いたテストが、直したい経路を通らないまま green になったことがある
2. 修正前の実装で失敗するテストを書き、意図したとおりの理由で失敗することを確認する
3. 修正を入れてテストを通す
4. 作業ツリー上で修正を打ち消し、テストが落ちることを確認する。確認できたら打ち消した差分を捨てる。この差分はコミットしない。落ちなければ原因を突き止める。同じラウンドの別の修正が同じ経路を直していた場合は、両方の修正を打ち消してテストが落ちることを確認し、どちらが効いたかを記録する。あわせてこの修正自体が要らなくなっていないかも判断する。それ以外はステップ 1 からやり直す。未検証のまま次のラウンドへ出さない

ステップ 2 を踏んでいればステップ 4 は形式的な確認になるが、省かない。同じラウンドで別の修正が入っていると、ステップ 2 の時点の失敗が再現しないことがある。修正を先に書いてしまったときはステップ 2 を踏めないので、ステップ 4 がその代わりになる。

**テストスイートがなくても、実行できるものは走らせる。** スクリプト、設定ファイル、hook、コマンドは、修正の前後で実際に動かして差を見るのが最低ライン。

**挙動の誤り以外の指摘も、指摘に応じて確認する。** 規約違反なら linter を通し、性能なら測り、記述の誤りなら出典と突き合わせる。

走らせようがないもの (ドキュメント、散文)、および走らせても修正の前後で差が出ないもの (コメント、命名の変更、挙動を変えない構造の整理) は、読み合わせで確かめる。修正した箇所と、それを参照している箇所を読み直して矛盾がないことを確認したと書く。引用や参照があるなら、引用元と突き合わせた、参照先の行が実在することを確かめた、も書く。

実行に手元で用意できない環境が要るもの (実セッションでしか発火しない hook、ログイン時にだけ効く設定など) は、走らせられない理由と、代わりに何を確かめたか (呼び出し側から辿った、構文チェックを通した、など) を書く。

**`検証なし` と書いてよいのは、読み合わせても判断できないものだけ。**その場合は、判断できない理由を書く。

記録には、テストを書いた経路ならステップ 2 の失敗理由とステップ 4 の結果を、走らせた経路なら前後で何がどう変わったかを書く。「4 ステップ実施済み」の一行では、レビュアーが妥当性を判定できない。

検証の結果は次の 4 つのどれかになる。ログの対応列にはこの語をそのまま書く。

- `実行` — 走らせて前後の差を見た
- `読み合わせ` — 走らせても差が出ない、または走らせようがないので、読んで確かめた
- `環境不足` — 差が出るはずだが、手元で用意できない環境が要るので、代替を確かめた
- `検証なし` — 何も確かめていない

区分が重なったときは、差が出るかで先に決める。差が出ないなら、環境を用意できるかによらず `読み合わせ`。差が出るはずだが手元で環境を用意できないなら `環境不足`。

**ここまでの条件を満たして記録された検証は、その種の修正に対する完全な検証として扱う。**より強い手段が実際に取れる場合を除いて、テストがない・実行していない・環境がないことを理由に不足としてはいけない。この一文がないと、懐疑的に振る舞うレビュアーが「読んだだけでは裏づけにならない」「構文が通ることと実際に発火することは別」と書け、依頼元は記録の文面を変えようがないまま毎ラウンド差し戻される。

対応結果 (修正の diff / 検証の内容 / 見送り理由 / 回答) は次ラウンドのレビュアーに渡すため記録しておく。
ループ内で作った修正コミットは以降のラウンドで検証されるため、ループ終了後に改めてセルフレビューを起動する必要はない。

#### 記録

記録は `.claude/artifacts/<branch>/self-review.md` に追記する。

- `feature/foo` なら `.claude/artifacts/feature/foo/self-review.md`
- `git branch --show-current` が空を返す detached HEAD では、`<branch>` の代わりに短縮コミットハッシュを使う
- ログは commit も push もしない
- run が終わったら削除する (削除の条件は 6)

run が正常に終わるたびに削除するので、通常は 1 つのファイルに 1 run 分しか入らない。ただし前回の run が打ち切りや中断で削除されずに残っていることがあるので、run ごとに見出しで区切る。区切りがないと、後からログを読むときにどこからが今回の run か分からない。

- run の見出しは `## run: <開始日時>`。日時は `date -Iseconds` を実行して得た値を使い、推測で書かない
- その下に、基準コミット・レビュー対象・依頼の要約を書く
- ラウンドの見出しは `### ラウンドN (<開始日時>)` として run の中に置く。ラウンドごとの日時から所要時間を出せる。`date -Iseconds` を実行し損ねて後から書く場合は、前ラウンドの最後の修正コミットの日時 (`git log -1 --format=%ad --date=iso-strict <コミット>`) で代用し、代用した旨を書く

日時をファイルの中に書くのは、ファイルシステムの mtime では足りないため。前回の run が残っている場合、mtime は最後に書き込んだ 1 回分しか示さず、どちらの run のものかを区別できない。基準コミットも書いておけば、`git show -s --format=%cI <基準>` で時期を裏から確認できる。

ラウンド1の見出しの下には、1 体・2 体のどちらで起動したかと、3 の判定で当てはまった信号 (何にも当てはまらず 1 体にしたなら「該当なし」) を 1 行書く。各ラウンドでは、レビュアーごとの担当観点・実際に動いたモデル・verdict を 1 行ずつ書く。1 体構成では担当観点を「セキュリティ+それ以外」のように書く。起動に失敗した、または結果が返らなかったレビュアーも 1 行書き、verdict の代わりに `失敗 (起動不可)` `結果なし (打ち切り)` のように記す。これを書かないと、そのレビュアーが指摘ゼロだったのか結果を返さなかったのかを後から区別できない。さらにヘッダ行と区切り行を置いて、指摘 1 件を 1 行ずつ追記する:

```
| 重大度 | 区分 | 該当箇所 | 指摘 | 対応 |
| --- | --- | --- | --- | --- |
```

- 区分はラウンド1では空欄、ラウンド2以降は `carried-over` / `regression` / `fresh-surface` / `new` (定義は 5)
- 対応は「修正 (コミットハッシュ / 検証: N)」「検証のみ (検証: N)」「見送り (理由)」「回答」「足切りで記録のみ (初出: ラウンドM)」のいずれか。`N` は 4 の検証の結果 (`実行` / `読み合わせ` / `環境不足` / `検証なし`)。「検証のみ」に `検証なし` は使わない。やり直しても判断できなかったなら「見送り」にして理由を書く。指摘の対象がこのログのメタ情報 (コミットハッシュの誤記、ラウンド見出しの日時など、検証の内容そのものではない部分) だった場合は、コミットが無いので「記録の修正 (検証: N)」と書く
- 検証の結果を列に出すのは、レビュアーが小見出しの欠落を探さずに済むようにするため。4 値にしてあるのは、正当な読み合わせを「検証なし」と書かせるとレビュアーが指摘し、記録の文面が変わらないまま毎ラウンド戻ってくるため
- 「足切りで記録のみ」は 5 の足切りが振り分けた結果。初出ラウンドを書くのは、同じ指摘が別ラウンドの別の行として再提出されたとき、5 の「これまでのラウンドで記録のみにした指摘」を照合できるようにするため
- セル内は要約でよいが、同じ指摘が別ラウンドで再提出されたときに同一だと分かる程度の具体性は残す。`|` は `\|` にエスケープする
- 修正の検証内容・見送り理由・question への回答は、要約だけでは次ラウンドのレビュアーが妥当性を判定できないので、全文をテーブルの下に指摘ごとの小見出しを立てて書く
- テストスイートのあるプロジェクトでは、ラウンドの見出しの直下に `スイート: N件 X.Xs green` の形で 1 行書く。基準時点から落ちているテストがあるなら `スイート: 120件 8.4s 3 failed (基準時点から既存)` のように書く。ラウンド1でも測って基準値にする。前のラウンドでコードを直したなら全体を走らせ、それ以外は前の値を再掲して `(再測なし)` と添える。テストを触らずに実装だけ直した修正でも実行時間は動くので、条件はテストの変更ではなくコードの変更に置く

### 5. ラウンド2以降: 検証レビュー

新しいレビュアー sub agent を `model: "opus"` で 1 つ起動し、記録ファイルのパスを伝える (これまでどおり内容はプロンプトに書き出さない)。結果を待つ間は「レビュアーを待つ間」のとおりにする。3 で結果が一度も得られなかった観点があれば、ラウンド2のレビュアーにその旨を伝える。ラウンド2の指摘のうち、その観点の内容に当たるものに規則0を適用するかは、指摘の中身から依頼元が判断する。

読む範囲も指示する。

- 今回の run の要約部分全体 (見出し・依頼の要約・各ラウンドのスイート行・指摘テーブル) は読む
- 直前ラウンドで対応した指摘の詳細 (検証内容・見送り理由・回答の全文) は読む
- それより前のラウンドの詳細は、対応が妥当か疑わしいと判断したときだけ読む。疑わなければそのラウンドで既に判定済みとして扱ってよい

区分 (`carried-over` / `regression` / `fresh-surface` / `new`) の判定に要るのは対応列のコミットハッシュのようなテーブルの情報で足りるので、詳細まで毎回読み直さなくていい。


このレビュアーの仕事:

- 依頼元が記録した検証を、修正の diff と追加したテストの実物に突き合わせて、その検証が修正を裏づけているかを判定する。記録だけを読んで判断しない。作業ツリーを変えない範囲 (テストやコマンドの実行) なら自分で再実行してよい。修正を打ち消して確かめる必要があるときは、指摘に書いて依頼元にやらせる
- 次のどれかに当たる修正は、それ自体を指摘する。検証が書かれていない / 「既存のスイートが green」しか書かれていない / 走らせられるものを走らせずに `検証なし` と書いている / 読み合わせれば判断できるものに `検証なし` と書いている / `環境不足` と書きながら、走らせられない理由か代替の確認を書いていない / テストで表現できる挙動の誤りなのに、ステップ 2 の失敗理由とステップ 4 の結果が書かれていない
- `実行` / `読み合わせ` / `環境不足` のいずれも、4 の条件を満たしていれば完全な検証として扱う。より強い手段が実際に取れる場合を除いて、テストがない・実行していない・環境がないことを理由に不足としてはいけない
- スイート行があれば、ラウンド1の値と比べる。実行時間がラウンド1の 2 倍以上になったか、60 秒以上増えていたら指摘する。隣接ラウンドの比較だと、毎ラウンド 1.5 倍ずつ増えても一度も引っかからない。テスト数が減っていたら、テストを消して green にしていないか確かめる
- 修正が新たな問題を持ち込んでいないか確認する
- 見送り理由と question への回答が妥当か判定する。妥当でなければ指摘を維持する
- 変更全体をあらためて 1 パス見て、新規の指摘がないか確認する

コミットメッセージはラウンド2以降のレビュー対象から外す。ループ中に積んだ修正コミットのメッセージは 6 の整理で書き直すので、ここで直しても消える。

レビュアーが結果を返さなかったときは 1 度だけ起動し直す。それでも返らなければそのラウンドは検証できていないので、ループを続けず、そこまでの結果をユーザーに報告して判断を仰ぐ。ログファイルの扱いは 6 の打ち切りと同じにする。

レビュアーには、指摘ごとに次のどれに当たるかを明示させる。

- `carried-over`: これまでのラウンドの指摘が未解消、見送り理由・回答が妥当でない、または修正の検証が記録されていない・記録された検証が修正を裏づけていない (4 の条件を満たして記録されたものを除く)。直前ラウンドより前の見送り理由・回答・検証は、疑わしいと判断しない限り妥当だったものとして扱う (5 冒頭の「読む範囲」を参照)
- `regression`: ループ中の修正が、それ以前からあった記述やコードを壊した。何ラウンド前の修正でも該当する
- `fresh-surface`: 直前のラウンドの修正コミットが追加した内容への指摘。まだどのラウンドのレビューも通っていない箇所
- `new`: 上のどれでもない、今回初めて出た指摘

足切りは重大度と区分の組み合わせで決まる。次の規則を上から順に適用し、指摘が複数の規則に当てはまるときは先に当てはまった規則を採る。

- 規則0: 3 の免除 (適用範囲は 3 を参照)
- 規則1: 事実として誤っている記述 (出典に存在しない引用、ツールやコマンドの仕様と矛盾する記述など、検証可能な事実の誤りに限る。検証や修正が十分かという評価はここに含まない) は足切りの対象外とし、重大度を問わず 4 に戻す。足切りは直す価値の低い指摘を落とす仕組みで、誤りを残す仕組みではない
- 規則2: これまでのラウンドで「足切りで記録のみ」にした指摘が再び出てきたら、重大度が must-fix に上がっていない限り、区分を問わず記録のみを維持する
- 規則3: 同じ修正の検証の記録に対する 2 回目以降の should-fix と nit は、`carried-over` でも 4 に戻さず記録のみにする。検証の記録は指摘のたびに書き直されるので、どのラウンドのレビューも通っていない状態が続き、書き方への指摘を無制限に戻せてしまう
- 規則4: `carried-over`、`regression` は重大度を問わず 4 に戻す
- 規則5: `new`、`fresh-surface` の must-fix は 4 に戻す
- 規則6: `new`、`fresh-surface` の question は 4 に戻して回答する。回答の結果修正が必要になったら次ラウンドへ進む。修正が不要だったときは回答を記録に残し、終了判定では 4 に戻す指摘として数えない
- 規則7: `new`、`fresh-surface` の should-fix と nit は、初出でも 4 に戻さず、対応を「足切りで記録のみ」としてログのテーブルに 1 行書く

規則0 の次に規則1を置くのは、事実誤りは足切りのどの状態よりも優先して直すべきだから。次に規則2・3が勝つので、記録済みの指摘が `carried-over` として再提出されても規則4には進まない。

`fresh-surface` の must-fix を `new` と揃えて規則5で拾うのは、直したばかりのコードのバグを記録するだけで終わらせないため (規則2により、一度記録のみにした指摘は重大度が must-fix に上がらない限りそのまま残る)。一方 should-fix と nit まで無条件に 4 へ戻すと、修正のたびに未レビュー面が生まれ、そこへの軽微な指摘がまた次の修正を呼ぶという、直すほど範囲が広がって不動点のないループになる。区分を「直前のラウンドの修正」に限ったうえで should-fix と nit を `new` と同じ規則7に掛けることで、同じ修正コミットへの言及は初出の 1 回で記録済みに落ち着く。

`fresh-surface` を `new` と区分として分けるのは、規則5〜7の結論を変えるためではない (両区分の扱いは同じ)。6 の打ち切り診断でどちらが非収束の原因かを切り分けるために、区分としては残している。

足切りを適用するのはラウンド2以降だけで、ラウンド1の指摘は重大度を問わず 4 で扱う。

### 6. 終了判定とユーザーへの報告

- 4 に戻す指摘がなくなったら終了。判定は区分と足切りの結果だけで行い、レビュアーの approve / request-changes は参考にしない。足切りで記録のみにした should-fix はレビュアーには未解消に見え続けるので、それが 1 件でも出た後は approve が返らなくなる (nit だけが記録のみになった場合は、レビュアーへの指示にある approve の条件どおり approve が返る)
- 回答だけで済んだ question は、次ラウンドが回ればそこで妥当性を判定される。そのラウンドで終了する場合は判定するレビュアーがいないので、回答をユーザーへの報告に含めて判断を仰ぐ
- ラウンド1を含め 5 ラウンド回っても収束しない場合は打ち切り、未解決の論点を整理してユーザーの判断を仰ぐ。あわせて区分の推移から原因を切り分けて報告する
  - `new` の must-fix が続く: ラウンド1の網羅性が足りない。ラウンド1を 1 体で起動していたなら、次に同種の変更が来たときは 2 体にすることを検討する
  - `fresh-surface` の must-fix が続く: 修正のスコープが広すぎて、修正のたびに大きな未レビュー面を作っている
  - `regression` が続く: 修正が既存を壊している
  - `carried-over` が続く: 修正が指摘を解消できていない、見送り理由・回答がレビュアーに却下され続けている、または検証を記録せずに次ラウンドへ出し続けている
- ループを終えたら、未 push のコミットを整理する。指摘対応のコミットを元のコミットへ畳む、メッセージを直すといった作業はここでまとめて行う。push 済みのコミットは整理しない
  - 非対話で組み直すには、`git commit --fixup` の後に `git rebase --autosquash <基準>` (Git 2.44 以降)。使えなければ基準コミットへ `git reset --hard` してから `git rev-list --reverse <基準>..<整理前のHEAD>` を 1 行ずつ `git cherry-pick` し、必要なコミットだけ `git commit --amend -F <メッセージ>` する
  - 整理の後に `git diff <整理前のHEAD> HEAD` が空であること、`git merge-base --is-ancestor <基準> HEAD` が通ること、基準コミットが upstream と一致することを確認する。組み直しのスクリプトが基準コミット自体を書き換える事故が起きうる
- 終了時、次をユーザーに要約して報告する
  - ラウンド数と各ラウンドのレビュアーの verdict
  - ラウンド1を 1 体・2 体のどちらで起動したか。2 体なら「セキュリティ」「それ以外」への割り当て、1 体ならその判定に至った理由 (何にも当てはまらなかった、など)
  - 指定したモデルと異なるモデルが動いたレビュアーがあれば、その観点とラウンド (ログを消す前にここへ出さないと、ユーザーに一度も届かないまま消える)
  - 修正した指摘
  - 見送った指摘とその理由
  - 足切りで記録のみにした指摘
  - 回答だけで済んだ question とその回答
  - `検証なし` とした修正と、判断できない理由
  - 検証のやり直しだけで閉じた指摘
  - ラウンド1で結果を返さなかったレビュアーがあればその事実 (起動し直しても結果が得られなかった観点を書く)
- 4 に戻す指摘がなくなって終了した場合は、報告を終えたらログファイルを削除する。run が終われば読む者がいなくなるうえ、レビュー本文と引用したコードがそのまま残り続けるので、報告した要約だけを記録として残す
- 打ち切りやレビュアー不応答で報告した場合は、ユーザーが続行しないと決めるまで削除しない。ログを残す旨とそのパスを報告に添える。続行する場合はログを残したまま次のラウンドに進む

## レビュアーへの指示

レビュアー sub agent のプロンプトには以下を含める。ラウンド2以降のレビュアーには、あわせて 4 の「修正の検証」の節をそのまま渡す。この手順は修正した側の義務なので、レビュアーがステップ 4 を自分で実行することはない、と添える。

### 役割と姿勢

- 人間のレビュアーが何も言うことがなくなる水準を目指す、懐疑的なレビュアーとして振る舞う
- 作者の説明を鵜呑みにせず、diff とコードベースから自分で理解を組み立てる
- 確信が持てない指摘は黙って流さず question として出す
- コードは変更せず、指摘の報告のみを行う。修正は依頼元のエージェントが行う

### ツールの積極活用

- **コード検索**: 変更した関数・メソッドの呼び出し元をすべて洗い出し影響範囲を確認する。類似実装や既存ヘルパーを探し、再実装 (車輪の再発明) を検出する。命名やイディオムの規約をコードベースから確認する
- **GitHub の Issue / PR 検索** (GitHub MCP を優先): 関連する過去の議論や設計判断、同種の変更が受けたレビュー指摘、変更箇所に関わる既知のバグを探す
- **Web 検索**: 使用しているライブラリ・API の仕様確認、deprecation や既知の問題、セキュリティアドバイザリの確認

### 出力形式

指摘ごとに以下を記す:

- 重大度: must-fix / should-fix / nit / question
- 区分 (ラウンド2以降のみ): `carried-over` / `regression` / `fresh-surface` / `new` — 定義は 5 にある。nit にも必ず付ける
- 該当箇所: `file:line`
- 根拠と、可能なら修正案

重大度で選別しない。確信が持てないものも含めて見つけた指摘は全部出す。絞り込みは依頼元が足切りで行う。

最後に approve / request-changes の判定を明示する。approve の条件は、must-fix / should-fix がゼロで、すべての question に納得できる回答が得られていること。nit だけが残っている場合は approve してよい。この判定はレビュアーの見解として受け取るだけで、ループを続けるかどうかは依頼元が区分と足切りで決める。

## レビュー観点

3 の「セキュリティ」グループには、以下の **セキュリティ** の項目 (共通・Webアプリ両方) に加えて、**依存関係** の既知の脆弱性と、**可観測性** のうち秘密情報の記録・漏洩に関わる部分を含める。それ以外の項目はすべて「それ以外」グループに含める。

### 共通

- **正しさ**: ロジックの誤り、境界値 (空、nil、0、負数、巨大入力、マルチバイト文字)、並行性・競合状態、エラー処理、リソースリーク
- **要求との一致**: ユーザーの依頼を過不足なく満たしているか。依頼にないスコープ外の変更が紛れ込んでいないか
- **影響範囲**: 変更した関数・メソッドのすべての呼び出し元で、挙動の変化が安全か
- **コードベースとの整合**: 既存の規約・命名・イディオムに沿っているか。既存のヘルパーで書けるものを再実装していないか
- **コメント**: CLAUDE.md のコメント規約に適合しているか。消すべきコメントが残っていないか
- **テスト**: 変更に見合うテストがあるか。境界・失敗系を覆っているか。実装をなぞるだけのテストになっていないか
- **セキュリティ**: 入力検証、インジェクション、秘密情報のハードコードやログ出力
- **性能**: 計算量、不要なループ・メモリ確保、I/O 回数
- **依存関係**: 追加・更新したライブラリの妥当性、既知の脆弱性
- **互換性**: 公開 API・シリアライズ形式・設定ファイルの後方互換性
- **可観測性**: 障害時に調査の手がかりになるログ・エラー情報が残るか
- **コミットメッセージ** (ラウンド1のみ): CLAUDE.md の規約 (概要、背景、不採用案、参考 URL) を満たすか。メッセージだけで変更内容と背景を理解できるか
- **ドキュメント**: README などの更新漏れ

### Webアプリの開発の場合

Ruby/Rails を主に想定するが、他言語の Web アプリにも読み替えて適用する。

- **DB クエリ**: N+1 (includes / preload の漏れ)、新しいクエリに対するインデックスの有無、不要な全件ロード
- **マイグレーション**: 可逆性、大きいテーブルでのロック、NOT NULL + default 追加の手順、コードとスキーマのデプロイ順序の安全性
- **整合性**: ユニーク制約が validation だけでなく DB 制約にもあるか、トランザクション境界、after_commit と after_save の使い分け
- **セキュリティ**: Strong Parameters / mass assignment、SQL インジェクション (文字列補間入りの where など)、XSS (html_safe / raw)、CSRF、オープンリダイレクト、認可漏れ (各エンドポイントで対象リソースの所有・権限チェックがあるか)、ファイルアップロードの検証
- **バックグラウンドジョブ**: 冪等性、リトライ安全性、引数にはオブジェクトでなく ID を渡しているか
- **時刻**: Time.current と Time.now の使い分け、タイムゾーン、日付境界の扱い
- **HTTP**: ステータスコードの妥当性、エラーレスポンス形式の一貫性
- **キャッシュ**: 無効化漏れ、キー設計
