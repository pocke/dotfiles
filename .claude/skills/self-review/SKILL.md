# セルフレビュー

## 目的

人間がこのコードをレビューするとき、何も言うことがない状態を作る。
レビューの所要時間やトークンコストの節約よりも、レビュー結果の完成度を優先する。
例外は、すでにレビューを一度通った箇所について ラウンド2以降で初めて出た should-fix と nit。これらはループを終わらせるために記録だけ残し、修正しない (5 のゲート)。

## 全体の流れ

1. レビュー対象の確定
2. プロジェクト固有のレビュー観点の収集
3. ラウンド1: 観点 × モデルのレビュアーを並行起動
4. 指摘のトリアージと対応 (修正と検証 / 検証のやり直し / 見送り理由の言語化 / question への回答)
5. ラウンド2以降: 検証レビュー (ここのゲートを 4 より先に通す)
6. 終了判定とユーザーへの報告

### 1. レビュー対象の確定

- スキル起動時に基準コミットを 1 つ確定する。基準は今回の作業を始める前の HEAD。セッションの記録から特定できない場合は upstream (なければデフォルトブランチ) との merge-base を使う
- 基準の確定時と各ラウンドの開始時に `git merge-base --is-ancestor <基準> HEAD` で基準が HEAD の祖先であることを検証する。rebase などで履歴が書き換わり祖先でなくなっていたら、upstream (なければデフォルトブランチ) との merge-base に基準を付け替える
- 以降すべてのラウンドで `git diff <基準>..HEAD` をレビュー対象とする。範囲を固定することで、ループ中に作った修正コミットも自動的に対象へ含まれる
- コミットメッセージはラウンド1だけレビューする。ラウンド2以降は対象外

### 2. プロジェクト固有のレビュー観点の収集

レビュアーを起動する前に、プロジェクト内のレビュー指針を探す。見つかったものはレビュアーのプロンプトに含める:

- プロジェクトの CLAUDE.md、`.claude/` 配下のドキュメント
- CONTRIBUTING.md、PULL_REQUEST_TEMPLATE、`docs/` 配下のコーディング・レビューガイド
- linter / formatter の設定 (.rubocop.yml など) から読み取れる規約

### 3. ラウンド1: 観点 × モデルのレビュアーを並行起動

変更の規模・性質に応じて、後述の「レビュー観点」を 2〜4 グループに分ける。**セキュリティ観点は必ず単独のグループにする** (グループごとにモデルの割り当てが違うため)。分け方の例:

- 正しさ・影響範囲 / 設計・規約・コメント / セキュリティ / 性能・テスト・コミットメッセージ

**観点グループ × モデルの直積でレビュアー sub agent を並行起動する。** モデルは `fable` / `opus` / `sonnet` の 3 つ。1 つのモデルが見落とした箇所を別のモデルが拾うので、残る死角は 3 モデルに共通するものだけになる。ラウンド1で取りこぼした must-fix は後続ラウンドまで残るうえ、5 のゲートはラウンド1の網羅性を前提にしているので、コストはここに集中させる。

- **セキュリティ観点のグループは `opus` と `sonnet` の 2 体、他のグループは 3 体**。上の 4 グループ例なら 11 体になる
- セキュリティ観点で `fable` を使わないのは、fable の bug-finding recall の優位が cybersecurity 領域の外に限ると提供元が明記しているため。加えて fable は攻撃的セキュリティ・生物学とライフサイエンス・要約された思考の抽出を対象とする分類器を持ち、正当なセキュリティ作業でも `stop_reason: "refusal"` を返すことがある。バイオ系のコードベースをレビューする場合は観点を問わず起こりうる (https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)
- `subagent_type` に `fork` を使ってはいけない。fork は `model` の指定を無視し、依頼元のコンテキストを引き継ぐので「作者の説明を鵜呑みにしない」独立性も失う
- レビュアーには他のレビュアーの存在を知らせない。同じ箇所を独立に見せるのが目的なので、分担していると伝えると和集合にならない
- レビュアー自身に sub agent を起こさせない。同時起動の上限は 20 で、超過分はキューに入らずエラーになる。子が上限に当たって落ちてもレビュアー自身は報告を返すので、調査の浅い報告が失敗と気づかれずに通る

指定したモデルで動くとは限らない。organization の allowlist でブロックされたモデルは、エラーではなく許可されたモデルに差し替わる。起動時の警告に気づいたら、記録には実際に動いたモデルを書く。

**結果の受け取りと重複排除**

- ラウンド1の全レビュアーの結果が揃うまで 4 に進まない。先に返った指摘から処理を始めると、後から来た同じ指摘をまとめられない
- 「レビュアーへの指示」の出力形式を満たす報告だけを結果と数える。refusal やエラーの返答、途中で打ち切られた報告は、結果が返らなかったものとして扱う
- 1 つのグループで全モデルが結果を返さなかったときは、`model` を指定せずに 1 体だけ起動し直す。打ち切りの原因はレート制限や一時的な障害のことが多い。それでも結果が得られなければ、そのグループの観点はレビューを一度も通っていないことになる。以降のラウンドでもその観点への指摘には 5 のゲートを適用せず、重大度を問わず 4 で扱う
- ラウンド1の全指摘を対象に、グループをまたいで、該当箇所と指摘内容が実質同じものを 1 件にまとめる。観点グループは互いに重なるので、別グループから同じ指摘が出る
- 重大度が割れたら高い方を採る。question と通常の重大度が割れたら通常の重大度を採り、question の内容は根拠に畳み込む
- 同じ箇所で結論が割れたもの (一方が「バグ」、他方が「仕様どおり」) は 1 件にまとめ、対立を残したまま 4 に渡す。4 は 1 件ずつ扱いを決める場所なので、対立が見えないと判断できない
- まとめた指摘には出したモデルを記録する。どのモデルが何を拾い、どこが重複したかは、モデルを増やした効果を後から測る材料になる

### 4. 指摘のトリアージと対応

レビュアーから受け取った各指摘について、必ずいずれかを行う。ラウンド2以降は 5 のゲートを通して 4 に戻された指摘だけがここに来る。

- **修正する**: コードを直して新しいコミットを積む。**ループ中は amend も rebase もしない**。5 の `fresh-surface` は「直前のラウンドの修正コミット」というコミットの同一性で判定するので、履歴を書き換えるとその判定対象が消える。ログに残した「修正 (コミットハッシュ)」も無効になる。未 push のコミットの整理は 6 でループを終えてから行う
- **修正しない**: 見送る理由を明文化する。「軽微だから」「時間がないから」は理由にならない。指摘自体が誤りである根拠、または修正がかえって悪化を招く根拠を書く
- **question に回答する**: 指摘が質問なら、調査した根拠を添えて回答する。回答の結果修正が必要と分かったら「修正する」に切り替える
- **検証をやり直す**: 検証が足りないと指摘されたら、下の検証を踏み直して記録する。コードを直したなら対応は「修正」、記録を足しただけなら「検証のみ」

**修正は検証してから次のラウンドへ出す。** 修正が効いているかの確認は、レビュアーではなく修正した側がやる。

**既存のテストスイートが green になったことは検証に数えない。** 指摘された不具合が未カバーなら修正前も green なので、緑でも修正の前後を区別できない。

挙動の誤りを指摘され、テストで表現できるなら、次の順で踏む (ユーザーの CLAUDE.md にあるバグ修正の手順に、前後のステップ 1 とステップ 4 を足したもの)。

1. 報告された失敗そのものを再現する。直す対象が実際にどう振る舞っているかを見てから書く。再現を飛ばして書いたテストが、直したい経路を通らないまま green になったことがある
2. 修正前の実装で失敗するテストを書き、意図したとおりの理由で失敗することを確認する
3. 修正を入れてテストを通す
4. 作業ツリー上で修正を打ち消し、テストが落ちることを確認する。確認できたら打ち消しを取り消す。この差分はコミットしない。落ちなければ原因を突き止めてステップ 1 からやり直し、未検証のまま次のラウンドへ出さない

ステップ 2 を踏んでいればステップ 4 は形式的な確認になるが、省かない。同じラウンドで別の修正が入っていると、ステップ 2 の時点の失敗が再現しないことがある。修正を先に書いてしまったときはステップ 2 を踏めないので、ステップ 4 がその代わりになる。

**テストスイートがなくても、実行できるものは走らせる。** スクリプト、設定ファイル、hook、コマンドは、修正の前後で実際に動かして差を見るのが最低ライン。

**挙動の誤り以外の指摘も、指摘に応じて確認する。** 規約違反なら linter を通し、性能なら測り、記述の誤りなら出典と突き合わせる。

「確認していない」と書いてよいのは、走らせようがないもの (ドキュメント、コメント、散文) だけ。その場合も何を確認したかは書く。引用元と突き合わせた、参照先の行が実在することを確かめた、といった内容になる。読み通せば分かることは、走らせようがないものに当たらない。

実行に手元で用意できない環境が要るもの (実セッションでしか発火しない hook、ログイン時にだけ効く設定など) は、走らせられない理由と、代わりに何を確かめたか (呼び出し側から辿った、構文チェックを通した、など) を書く。

記録には、テストを書いた経路ならステップ 2 の失敗理由とステップ 4 の結果を、走らせた経路なら前後で何がどう変わったかを書く。「4 ステップ実施済み」の一行では、レビュアーが妥当性を判定できない。

対応結果 (修正の diff / 検証の内容 / 見送り理由 / 回答) は次ラウンドのレビュアーに渡すため記録しておく。
ループ内で作った修正コミットは以降のラウンドで検証されるため、ループ終了後に改めてセルフレビューを起動する必要はない。

記録は `.claude/artifacts/<branch>/self-review.md` に追記する。

- `feature/foo` なら `.claude/artifacts/feature/foo/self-review.md`
- `git branch --show-current` が空を返す detached HEAD では、`<branch>` の代わりに短縮コミットハッシュを使う
- ログは commit も push もしない

同じブランチで何度も起動すると 1 つのファイルに積み上がるので、run ごとに見出しで区切る。区切りがないと、後からログを読むときにどこからが今回の run か分からない。

- run の見出しは `## run: <開始日時>`。日時は `date -Iseconds` を実行して得た値を使い、推測で書かない
- その下に、基準コミット・レビュー対象・依頼の要約を書く
- ラウンドの見出しは `### ラウンドN (<開始日時>)` として run の中に置く。ラウンドごとの日時から所要時間を出せる

日時をファイルの中に書くのは、ファイルシステムの mtime では足りないため。1 つのファイルに複数の run が入るので mtime は最後の 1 回しか示せず、ログを別の場所へ集めたり分析中に触ったりすると変わる。基準コミットも書いておけば、`git show -s --format=%cI <基準>` で時期を裏から確認できる。

各ラウンドでは、レビュアーごとの担当観点・実際に動いたモデル・verdict を 1 行ずつ書く。起動に失敗した、または結果が返らなかったレビュアーも 1 行書き、verdict の代わりに `失敗 (起動不可)` `結果なし (打ち切り)` のように記す。これを書かないと、そのモデルが指摘ゼロだったのか結果を返さなかったのかを後から区別できない。さらにヘッダ行と区切り行を置いて、指摘 1 件を 1 行ずつ追記する:

```
| 重大度 | 区分 | 該当箇所 | 指摘 | 対応 | モデル |
| --- | --- | --- | --- | --- | --- |
```

- 区分はラウンド1では空欄、ラウンド2以降は `carried-over` / `regression` / `fresh-surface` / `new` (定義は 5)
- 対応は「修正 (コミットハッシュ / 検証あり・なし)」「見送り (理由)」「回答」「検証のみ」「ゲートで記録のみ (初出: ラウンドN)」のいずれか。検証の有無を対応列に出すのは、レビュアーが小見出しの欠落を探さずに済むようにするため。「ゲートで記録のみ」は 5 のゲートが振り分けた結果。初出ラウンドを書くのは、同じ指摘が別ラウンドの別の行として再提出されたとき、5 の「これまでのラウンドで記録のみにした指摘」を照合できるようにするため
- モデル列には、ラウンド1でその指摘を出したモデルを書く。複数のモデルが同じ指摘を出していたら `fable` / `opus` のように全部並べる。ラウンド2以降は空欄
- セル内は要約でよい。`|` は `\|` にエスケープする
- 修正の検証内容・見送り理由・question への回答は、要約だけでは次ラウンドのレビュアーが妥当性を判定できないので、全文をテーブルの下に指摘ごとの小見出しを立てて書く
- テストスイートのあるプロジェクトでは、ラウンドの見出しの直下に `スイート: N件 X.Xs green` の形で 1 行書く。毎ラウンド全体を走らせ、ラウンド1でも測って基準値にする。修正が実行時間を跳ね上げても、記録がないと誰も気づかない

### 5. ラウンド2以降: 検証レビュー

新しいレビュアー sub agent を `model: "opus"` で 1 つ起動し、これまでの全ラウンドの指摘一覧と対応内容を渡す (4 の記録ファイルを渡せば足りる)。前ラウンド分だけでは、何ラウンド前の修正が持ち込んだ問題かを判定できず、過去にゲートで記録のみにした指摘も識別できない。

モデルを明示するのは、ラウンド2以降が 1 体で全観点を見るため。`fable` が当たると、セキュリティ観点で bug-finding recall の優位がないうえ、正当なセキュリティ作業でも `stop_reason: "refusal"` を返してそのラウンドの検証がまるごと失われる。ラウンド1と違って同じ範囲を見る別のモデルがいないので、取り返しがつかない。`model` を省略すると依頼元のモデルになるとは限らない (`subagent_type` の定義にモデルがあればそちらが優先される) ので、省略では避けられない。

このレビュアーの仕事:

- 依頼元が記録した検証を、修正の diff と追加したテストの実物に突き合わせて、その検証が修正を裏づけているかを判定する。記録だけを読んで判断しない。作業ツリーを変えない範囲 (テストやコマンドの実行) なら自分で再実行してよい。修正を打ち消して確かめる必要があるときは、指摘に書いて依頼元にやらせる
- 次のどれかに当たる修正は、それ自体を指摘する。検証が書かれていない / 「既存のスイートが green」しか書かれていない / 走らせられるものを走らせずに「確認していない」と書いている
- ラウンド間でスイートを比べる。実行時間が 2 倍かつ 30 秒以上増えていたら指摘する。テスト数が減っていたら、テストを消して通していないか確かめる
- 修正が新たな問題を持ち込んでいないか確認する
- 見送り理由と question への回答が妥当か判定する。妥当でなければ指摘を維持する
- 変更全体をあらためて 1 パス見て、新規の指摘がないか確認する

コミットメッセージはラウンド2以降のレビュー対象から外す。ループ中に積んだ修正コミットのメッセージは 6 の整理で書き直すので、ここで直しても消える。

レビュアーが結果を返さなかったときは 1 度だけ起動し直す。それでも返らなければそのラウンドは検証できていないので、ループを続けず、そこまでの結果をユーザーに報告して判断を仰ぐ。

レビュアーには、指摘ごとに次のどれに当たるかを明示させる。

- `carried-over`: これまでのラウンドの指摘が未解消、見送り理由・回答が妥当でない、または修正の検証が記録されていない・記録された検証が修正を裏づけていない
- `regression`: ループ中の修正が、それ以前からあった記述やコードを壊した。何ラウンド前の修正でも該当する
- `fresh-surface`: 直前のラウンドの修正コミットが追加した内容への指摘。まだどのラウンドのレビューも通っていない箇所
- `new`: 上のどれでもない、今回初めて出た指摘

ゲートの基準は「その箇所がレビューを一度通ったか」。通っていない箇所は重大度を問わず拾い、通った箇所への新規指摘は must-fix と question だけ拾う。受け取った指摘は依頼元がこう振り分ける。

- `carried-over`、`regression`、`fresh-surface` は重大度を問わず 4 に戻す
- `new` の must-fix は 4 に戻す
- `new` の question は 4 に戻して回答する。回答の結果修正が必要になったら次ラウンドへ進む。修正が不要だったときは回答を記録に残し、終了判定では 4 に戻す指摘として数えない
- `new` の should-fix と nit は 4 に戻さず、対応を「ゲートで記録のみ」としてログのテーブルに 1 行書く
- これまでのラウンドで「ゲートで記録のみ」にした指摘が再び出てきたら、重大度が must-fix に上がっていない限り、区分を問わず記録のみを維持する
- 例外として、事実として誤っている記述 (出典に存在しない引用、ツールやコマンドの仕様と矛盾する記述) はゲートの対象外とし、重大度を問わず 4 に戻す。ゲートは直す価値の低い指摘を落とす仕組みで、誤りを残す仕組みではない

`fresh-surface` を `new` と分ける理由。修正コミットが追加した散文やメッセージは、その時点でどのラウンドのレビューも通っていないので、一度は重大度を問わず拾う必要がある。一方これを何ラウンドも `regression` として拾い続けると、修正のたびに未レビュー面が増えて指摘が湧き続け、ループが終わらない。区分を「直前のラウンドの修正」に限ることで、どの修正コミットもちょうど 1 回だけ全重大度のレビューを受け、その次のラウンドからは `new` と同じ扱いになる。

`new` の should-fix と nit でループを延ばさないのは、その箇所がすでにレビューを一度通っているため。懐疑的に見ろと指示されたレビュアーはまっさらな状態で全体を見るたびに何かしら出すので、これを無条件に拾うとループが終わらない。ラウンド1は観点グループ × モデルの直積で回すので、どの箇所も複数のモデルのレビューを通っている。ゲートを適用するのはラウンド2以降だけで、ラウンド1の指摘は重大度を問わず 4 で扱う。

### 6. 終了判定とユーザーへの報告

- 4 に戻す指摘がなくなったら終了。判定は区分とゲートの結果だけで行い、レビュアーの approve / request-changes は参考にしない。ゲートで記録のみにした指摘はレビュアーには未解消に見え続けるので、それが 1 件でも出た後は approve が返らなくなる
- 回答だけで済んだ question は、次ラウンドが回ればそこで妥当性を判定される。そのラウンドで終了する場合は判定するレビュアーがいないので、回答をユーザーへの報告に含めて判断を仰ぐ
- ラウンド1を含め 5 ラウンド回っても収束しない場合は打ち切り、未解決の論点を整理してユーザーの判断を仰ぐ。あわせて区分の推移から原因を切り分けて報告する
  - `new` の must-fix が続く: ラウンド1の網羅性が足りない
  - `fresh-surface` が続く: 修正のスコープが広すぎて、修正のたびに大きな未レビュー面を作っている
  - `regression` が続く: 修正が既存を壊している
  - `carried-over` が続く: 修正が指摘を解消できていない、見送り理由・回答がレビュアーに却下され続けている、または検証を記録せずに次ラウンドへ出し続けている
- ループを終えたら、未 push のコミットを整理する。指摘対応のコミットを元のコミットへ畳む、メッセージを直すといった作業はここでまとめて行う。push 済みのコミットは整理しない
  - 非対話で組み直すには、`git commit --fixup` の後に `git rebase --autosquash <基準>` (Git 2.44 以降)。使えなければ基準コミットへ `git reset --hard` してから `git rev-list --reverse <基準>..<整理前のHEAD>` を 1 行ずつ `git cherry-pick` し、必要なコミットだけ `git commit --amend -F <メッセージ>` する
  - 整理の後に `git diff <整理前のHEAD> HEAD` が空であること、`git merge-base --is-ancestor <基準> HEAD` が通ること、基準コミットが upstream と一致することを確認する。組み直しのスクリプトが基準コミット自体を書き換える事故が起きうる
  - 整理でハッシュが変わるので、ログの冒頭に整理前後の対応表を書き足す
- 終了時、次をユーザーに要約して報告する。ログを書いた場合は詳細がログファイルにあることを、パスを添えて伝える
  - ラウンド数と各ラウンドのレビュアーの verdict
  - 修正した指摘
  - 見送った指摘とその理由
  - ゲートで記録のみにした指摘
  - 回答だけで済んだ question とその回答
  - 検証していない修正と、その理由
  - ラウンド1で結果を返さなかったレビュアーがあればその事実 (全モデルが返さなかった観点と、一部のモデルだけ返さなかった観点を分けて書く)

## レビュアーへの指示

レビュアー sub agent のプロンプトには以下を含める。ラウンド2以降のレビュアーには、あわせて 4 の検証の手順を判定基準として渡す。

### 役割と姿勢

- 人間のレビュアーが何も言うことがなくなる水準を目指す、懐疑的なレビュアーとして振る舞う
- 作者の説明を鵜呑みにせず、diff とコードベースから自分で理解を組み立てる
- 確信が持てない指摘は黙って流さず question として出す
- コードは変更せず、指摘の報告のみを行う。修正は依頼元のエージェントが行う

### ツールの積極活用

- **コード検索**: 変更した関数・メソッドの呼び出し元をすべて洗い出し影響範囲を確認する。類似実装や既存ヘルパーを探し、再実装 (車輪の再発明) を検出する。命名やイディオムの規約をコードベースから確認する
- **GitHub の Issue / PR 検索** (GitHub MCP を優先): 関連する過去の議論や設計判断、同種の変更が受けたレビュー指摘、変更箇所に関わる既知のバグを探す
- **Web 検索**: 使用しているライブラリ・API の仕様確認、deprecation や既知の問題、セキュリティアドバイザリの確認

### 出力形式

指摘ごとに以下を記す:

- 重大度: must-fix / should-fix / nit / question
- 区分 (ラウンド2以降のみ): `carried-over` / `regression` / `fresh-surface` / `new` — 定義は 5 にある。nit にも必ず付ける
- 該当箇所: `file:line`
- 根拠と、可能なら修正案

重大度で足切りしない。確信が持てないものも含めて見つけた指摘は全部出す。絞り込みは依頼元がゲートで行う。

最後に approve / request-changes の判定を明示する。approve の条件は、must-fix / should-fix がゼロで、すべての question に納得できる回答が得られていること。nit だけが残っている場合は approve してよい。この判定はレビュアーの見解として受け取るだけで、ループを続けるかどうかは依頼元が区分とゲートで決める。

## レビュー観点

### 共通

- **正しさ**: ロジックの誤り、境界値 (空、nil、0、負数、巨大入力、マルチバイト文字)、並行性・競合状態、エラー処理、リソースリーク
- **要求との一致**: ユーザーの依頼を過不足なく満たしているか。依頼にないスコープ外の変更が紛れ込んでいないか
- **影響範囲**: 変更した関数・メソッドのすべての呼び出し元で、挙動の変化が安全か
- **コードベースとの整合**: 既存の規約・命名・イディオムに沿っているか。既存のヘルパーで書けるものを再実装していないか
- **コメント**: CLAUDE.md のコメント規約に適合しているか。消すべきコメントが残っていないか
- **テスト**: 変更に見合うテストがあるか。境界・失敗系を覆っているか。実装をなぞるだけのテストになっていないか
- **セキュリティ**: 入力検証、インジェクション、秘密情報のハードコードやログ出力
- **性能**: 計算量、不要なループ・メモリ確保、I/O 回数
- **依存関係**: 追加・更新したライブラリの妥当性、既知の脆弱性
- **互換性**: 公開 API・シリアライズ形式・設定ファイルの後方互換性
- **可観測性**: 障害時に調査の手がかりになるログ・エラー情報が残るか
- **コミットメッセージ** (ラウンド1のみ): CLAUDE.md の規約 (概要、背景、不採用案、参考 URL) を満たすか。メッセージだけで変更内容と背景を理解できるか
- **ドキュメント**: README などの更新漏れ

### Webアプリの開発の場合

Ruby/Rails を主に想定するが、他言語の Web アプリにも読み替えて適用する。

- **DB クエリ**: N+1 (includes / preload の漏れ)、新しいクエリに対するインデックスの有無、不要な全件ロード
- **マイグレーション**: 可逆性、大きいテーブルでのロック、NOT NULL + default 追加の手順、コードとスキーマのデプロイ順序の安全性
- **整合性**: ユニーク制約が validation だけでなく DB 制約にもあるか、トランザクション境界、after_commit と after_save の使い分け
- **セキュリティ**: Strong Parameters / mass assignment、SQL インジェクション (文字列補間入りの where など)、XSS (html_safe / raw)、CSRF、オープンリダイレクト、認可漏れ (各エンドポイントで対象リソースの所有・権限チェックがあるか)、ファイルアップロードの検証
- **バックグラウンドジョブ**: 冪等性、リトライ安全性、引数にはオブジェクトでなく ID を渡しているか
- **時刻**: Time.current と Time.now の使い分け、タイムゾーン、日付境界の扱い
- **HTTP**: ステータスコードの妥当性、エラーレスポンス形式の一貫性
- **キャッシュ**: 無効化漏れ、キー設計
