## ソースコード中のコメント

**既定値は「書かない」**。書いて良いのは、**コードを読んでも分からない外部情報** だけ。

書いて良いコメントの例:
- 既知のバグ/制約への参照 (例: `# https://...issues/N の影響でこの順序が必須`)
- 準拠した仕様への参照 (例: `https://html.spec.whatwg.org/` 内へのリンク)
- 隠れた invariant (例: `# Caller must hold the lock`)
- 仕様の罠 (例: `# Returns 0, not nil, when empty`)
- 一見して意図が分かりづらい実装

### 書こうとしたコメントが以下に該当したら書かない

書いてしまっていたら消す。

1. コミットメッセージや PR description に書くべき内容 (背景、選択肢、参考 URL、移行履歴)
2. 判断や意図の retrospect (NG: 「〜したいので」「〜のため」)
3. コードの動作をそのまま自然言語に翻訳 (NG: 「X して Y する」「Z を更新する」)
4. workaround や smell の justify (NG: 「本来は X だが Y する」「現状の制約で」 → workaround を直すか TODO で明示)
5. 「以前は X だったが今は Y」のような移行中の状態 (NG: git log に任せる)

迷ったら書かない。コミット前に全コメントを見直し、「消しても読み手は困らない」ものは消す。

### 一見して意図が分かりづらい実装にコメントを書くとき

「もっと素直な書き方があるのでは?」「なぜこうしてる?」と読み手が立ち止まりそうなコードには、その疑問への先回り回答をコメントで書く。

書き方:
- **読み手が陥りがちな自然な発想** と **実際そうしていない理由** を対比する
  - GOOD: `# bar! は X のとき副作用が出るため、ここでは baz! を使う`
- 識別子や構造で表現できる部分はコード側で表現し、**残った非自明性** だけをコメントにする
- retrospect (「〜したいので」「〜のため」) ではなく、**因果** で書く
  - BAD: `# baz! を使いたい` ← retrospect (NG #2)
  - BAD: `# baz! を呼んでいる` ← 翻訳 (NG #3)

判断に迷ったら書かない。書くか書かないかが拮抗するときは、**まず識別子改善やメソッド分割でコードを読みやすくして、コメント不要に持ち込めないか** を先に検討する。

## Git の扱い

コードに何かしら変更を加えた場合、最後にgit commitをして。1回の命令内に複数の指示が含まれている場合、1つの指示ごとにコミットを分けて。

コミットメッセージは英語で書いて。コミットメッセージの1行目にはそのコミットの概要を簡潔にまとめて。
2行目以降には実装の詳細と、背景情報として必要となる情報を書いて。コミットメッセージを読めばコミットの変更内容、その変更に至った背景、取らなかった選択肢などが分かるように、詳細に書いて。変更を行う際に調査して参考としたURLなどは可能な限りコミットメッセージに含めて。
コミットメッセージの最後に、本文から1行空けて下記の「一句・一首」と同様のルールで俳句、川柳あるいは短歌を詠んで1行で記して。この行のみは日本語で書いて。

git add と git commit は`&&`で繋げず、2回のコマンド実行に分けて。

## GitHubへのアクセス

GitHub のデータにアクセスする際は、`gh`コマンドよりもGitHub MCPを優先して。

## 一句・一首

返答の最後に、50%の確率で俳句あるいは川柳を、50%の確率で短歌を詠んで。
季節を意味する"春", "夏", "秋", "冬"の文字は詩の中に含んではいけない。
過度な字余り・字足らずも避けること。

## セルフレビュー

なんらかの変更を行いコミットした後、self-review skillを起動してセルフレビューを行って。手順とレビュー観点はskill側に書いてある。
これは変更がごく小さい場合 (typo修正、コメントのみの変更など) には必要ない。
GitHubへのpush, PR作成を含む場合、セルフレビューはGitHubへのpush, PR作成の前に行って。
