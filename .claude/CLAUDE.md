## 日本語の文体

返答、ソースコード中のコメント、PR description、ドキュメントなど、日本語で書くすべての文章に適用する。

原則は2つ:

1. **翻訳調を書かない**。書く前に「これは英語のどの表現の直訳か?」を自問し、英語の慣用句が透けて見えるなら日本語として自然な表現に組み替える (逆翻訳テスト)
2. **抽象語でぼかさず、具体的な事実で書く**。読み手がその文だけから挙動・条件を再構成できること

### 書かないもの

書いてしまっていたら直す。

1. 中身のない評価語 (「適切に」「正しく」「堅牢に」「効率的に」)。何がどう適切なのかを書く
   - NG: 「エラーを適切にハンドリングするようにした」
   - GOOD: 「接続エラー時は最大3回リトライし、それでも失敗したら例外を投げるようにした」
2. ぼかした可能性表現 (may / potential の直訳)。何が・どの条件で起きるかを書く
   - NG: 「意図しない動作を引き起こす可能性があります」
   - GOOD: 「posts が空のとき NoMethodError で落ちる」
3. ensure / allow の直訳定型
   - NG: 「接続が閉じられることを確実にします」 → GOOD: 「必ず接続を閉じる」
   - NG: 「並列実行を可能にします」 → GOOD: 「並列に実行できるようになる」
4. 英語の受動態をなぞった受け身の連鎖。動作主を主語に立てて能動で書く
   - NG: 「リクエストが受信されると、バリデーションが実行され、エラーが返されます」
   - GOOD: 「リクエストを受け取るとバリデーションを実行し、エラーを返す」
5. 冗長な言い回し
   - NG: 「〜することができます」 → GOOD: 「〜できる」
   - NG: 「〜の実行を行う」 → GOOD: 「〜を実行する」
6. 文頭の定型句の機械的な連発 (「これにより、」「なお、」「注意してください。」)。因果は「〜ので」「〜ため」として文の中に織り込む
7. 機構を「ゲート」のような比喩で名指しするだけで判定の中身を書かない書き方。何が何を判定してどうなるかを具体的に書く
   - NG: 「デプロイ前にゲートを 1 段入れた」
   - GOOD: 「デプロイ前にテストを走らせ、落ちていたら止めるようにした」

定着した技術用語のカタカナ語 (API、デッドロック、コンテキストウィンドウ、ゲートウェイ、論理ゲート等) はそのまま使ってよい。
このリストは網羅ではない。読みづらい表現に気づいたら NG/GOOD の対で追記して育てる。

## ソースコード中のコメント

**既定値は「書かない」**。書いて良いのは、**コードを読んでも分からない外部情報** だけ。

書いて良いコメントの例:
- 既知のバグ/制約への参照 (例: `# https://...issues/N の影響でこの順序が必須`)
- 準拠した仕様への参照 (例: `https://html.spec.whatwg.org/` 内へのリンク)
- 隠れた invariant (例: `# Caller must hold the lock`)
- 仕様の罠 (例: `# Returns 0, not nil, when empty`)
- 一見して意図が分かりづらい実装

### 書こうとしたコメントが以下に該当したら書かない

書いてしまっていたら消す。

1. コミットメッセージや PR description に書くべき内容 (背景、選択肢、参考 URL、移行履歴)
2. 判断や意図の retrospect (NG: 「〜したいので」「〜のため」)
3. コードの動作をそのまま自然言語に翻訳 (NG: 「X して Y する」「Z を更新する」)
4. workaround や smell の justify (NG: 「本来は X だが Y する」「現状の制約で」 → workaround を直すか TODO で明示)
5. 「以前は X だったが今は Y」のような移行中の状態 (NG: git log に任せる)

迷ったら書かない。コミット前に全コメントを見直し、「消しても読み手は困らない」ものは消す。

### 一見して意図が分かりづらい実装にコメントを書くとき

「もっと素直な書き方があるのでは?」「なぜこうしてる?」と読み手が立ち止まりそうなコードには、その疑問への先回り回答をコメントで書く。

書き方:
- **読み手が陥りがちな自然な発想** と **実際そうしていない理由** を対比する
  - GOOD: `# bar! は X のとき副作用が出るため、ここでは baz! を使う`
- 識別子や構造で表現できる部分はコード側で表現し、**残った非自明性** だけをコメントにする
- retrospect (「〜したいので」「〜のため」) ではなく、**因果** で書く
  - BAD: `# baz! を使いたい` ← retrospect (NG #2)
  - BAD: `# baz! を呼んでいる` ← 翻訳 (NG #3)

判断に迷ったら書かない。書くか書かないかが拮抗するときは、**まず識別子改善やメソッド分割でコードを読みやすくして、コメント不要に持ち込めないか** を先に検討する。

## テスト

テストを書くときは TDD の Red-Green-Refactor のサイクルを意識して。

1. **Red**: まず失敗するテストを書き、実際に失敗することを確認する
2. **Green**: テストが通る最小限の実装をする
3. **Refactor**: テストを green に保ったままコードを整える

特にバグ修正では、次の順序を必ず守って。

1. 問題が修正された前提で、修正前の実装では失敗するテストを書く
2. そのテストを実行し、**意図したとおりに失敗すること** を確認する (期待どおりの理由で落ちているかを見る)
3. 実装を修正してテストを green にする

「先に実装を直してからテストを書く」のは避けて。テストが本当にそのバグを捕捉できているかを保証できないため。

### テストしないもの

フレームワーク、言語が提供する機能自体のテストは行わない。

Ruby/Railsを例に挙げると次のようになる。他の言語やフレームワークでも同様に扱う。

* `validates :name, presence: true`と書かれたモデルのテストとして、`User.new(name: nil).valid?` が false になることのテストは書かない。
* `attr_accessor` などで代入した値がそのまま読めることのテストは書かない。

これらのテストはそのフレームワーク自身のテストであり、アプリケーションのテストではない。
ただし、これらの宣言を利用した実装がある場合は、当然それはテスト対象となる。先ほどの例だと、バリデーションエラーに対してユーザーフィードバックなどの処理を行っていれば、それはテスト対象である。

## Git の扱い

コードに何かしら変更を加えた場合、最後にgit commitをして。1回の命令内に複数の指示が含まれている場合、1つの指示ごとにコミットを分けて。

コミットメッセージは英語で書いて。コミットメッセージの1行目にはそのコミットの概要を簡潔にまとめて。
2行目以降には実装の詳細と、背景情報として必要となる情報を書いて。コミットメッセージを読めばコミットの変更内容、その変更に至った背景、取らなかった選択肢などが分かるように、詳細に書いて。変更を行う際に調査して参考としたURLなどは可能な限りコミットメッセージに含めて。

`master`, `main`, `develop`, `release` へは push しないで。リポジトリの default branch がこれ以外の名前ならそれも同じ。push 先がこれらのブランチになるなら、実行する前に必ず確認を取って。topic branch を push して PR を作る形にする。


## Pull Request

PR を作成するときの title と description の規約。

- 記述する内容はコミットメッセージの規約に合わせる。title は 1 行目の概要と同じ要領で書き、description には変更内容・背景・取らなかった選択肢・参考 URL を書く。description だけ読めばレビューを始められる状態にする
- PR が複数コミットを含む場合、コミットメッセージの寄せ集めにせず、PR 全体として 1 つの文章に書き直す
- 言語は次の順で決める:
  1. 明示的な指示 (依頼、プロジェクトの CLAUDE.md 等) があればそれに従う
  2. なければ `gh pr list --state all --limit 5 --json title,body` を実行し、取得した PR の title と body で多数派の言語に合わせる
  3. 判断材料が無ければ、コミットメッセージと同じ英語で書く
- 日本語で書く場合は「日本語の文体」の規約を適用する

## 一句・一首

返答の最後に、50%の確率で俳句あるいは川柳を、50%の確率で短歌を詠んで。
詠むのは返答のみ。コミットメッセージや PR description には書かない。
季節を意味する"春", "夏", "秋", "冬"の文字は詩の中に含んではいけない。
過度な字余り・字足らずも避けること。

## セルフレビュー

なんらかの変更を行いコミットした後、self-review skillを起動してセルフレビューを行って。手順とレビュー観点はskill側に書いてある。
これは変更がごく小さい場合 (typo修正、コメントのみの変更など) には必要ない。
GitHubへのpush, PR作成を含む場合、セルフレビューはGitHubへのpush, PR作成の前に行って。
